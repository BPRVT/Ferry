# Ferry 8.0.0 — a presentation clock

**Status: draft. No code written. Nothing here is agreed.**

This is a design document for the change that would stop the picture being choppy. It is written
before implementation on purpose: 8.0.0 touches the render path, the audio path, and the
relationship between them, and this project's history says that confident changes to the video
pipeline made without a plan cost three releases each time.

---

## 1. The symptom, and what is already known

Reported from hardware, across several releases and in these words: *"when it lags or falls behind
it's SO choppy"*, and after 7.6.0, *"a little smoother but still a little choppy here and there."*

What the logs establish, and it is worth being precise because it rules a lot out:

| Observation | Source | What it rules out |
|---|---|---|
| `DEC drops 8, kf 0, qdrop 0%` over a whole session | live log | Decode capacity. The decoder is not struggling. |
| 1046×720 at 51 fps, panel 59.94 Hz | live log | Bandwidth, and resolution. The panel can show every frame with room spare. |
| 42% of frames skipped at the render step | live log | Even delivery — this is *arithmetically impossible* at 51 fps into 59.94 Hz unless arrival is bunched. |
| Audio queue 0 → 32 (full) in ~200 ms | live log | Any doubt about bunching. The same burst, seen from the other stream. |
| Still choppy after 7.6.0 | user | That the burst *budget* alone is sufficient. |

**The pipeline is healthy. The frames arrive, decode, and are correct. They reach the screen at
uneven moments, and unevenness is what the eye reports as choppy.**

7.6.0 stopped Ferry discarding frames the panel could have shown. That was necessary and it helped.
It cannot have been sufficient, and the reason is structural: 7.6.0 changed *whether* a frame is
shown, and choppiness is a question of *when*.

## 2. The root cause, stated plainly

**Ferry has no presentation clock.** It renders every frame the instant the decoder produces it —
`releaseOutputBuffer(index, render)`, "show this as soon as possible."

That is the lowest-latency choice available and the least smooth one. It makes display timing a
direct function of network arrival timing. Wi-Fi delivers in clumps; the panel therefore updates in
clumps. No amount of deciding *which* frames to show can fix uneven *timing*, because the
information needed — when this frame should appear — is never computed.

Every real video player solves this the same way: give each frame a scheduled presentation time,
hold it briefly, and release it at that moment. The buffer that makes this possible costs latency.
That is the entire trade.

## 3. The three inputs Ferry already receives and throws away

This is the part that reframes 8.0.0 from "add a jitter buffer" to "use what is already on the wire."

1. **The mirror packet header.** Every video packet is preceded by a **128-byte** header. Ferry
   reads **six bytes** of it — `payloadSize` at offset 0, `payloadType` at offset 4 — and discards
   the other 122. UxPlay's `raop_rtp_mirror.c`, which this implementation is derived from, reads a
   timestamp from that header. The original handshake plan for this feature
   (`2026-06-08-airplay2-mirroring-handshake.md`, Step 1) explicitly lists extracting
   "`payloadSize`, `payloadType`, and `timestamp`". The timestamp was never implemented.

2. **`TimingHandler.rtpClockOffsetUs`.** Computed on every NTP probe, from a full working
   implementation of the timing protocol. Its own KDoc says: *"Nothing consumes it."*

3. **`AirPlayNtpClient`'s replies.** Ferry polls the sender's timing port every two seconds — it has
   to, or macOS will not start the stream — logs the first four responses, and discards every one.

**Ferry runs a complete clock-synchronisation implementation in order to satisfy the sender, and
then throws the answer away.** Meanwhile the decoder is fed a fabricated presentation timestamp:
`framePtsUs += 1_000_000/60` per frame, regardless of the real rate, which is fiction the moment the
sender is not at exactly 60 fps.

## 4. The trade, and the constraint that shapes it

The user's position, verbatim: *"I'm fine if the iPad is playing a little ahead while the TV is
smooth, not choppy **and audio is synced**."*

The second half is the load-bearing part and it decides the architecture.

Delaying video without delaying audio does not trade latency for smoothness. It trades smoothness
for **lip-sync error**, which is far more objectionable and which 6.8.0 spent a whole release
fixing. So:

> **8.0.0 cannot be a video-only change.** Video presentation delay and audio presentation delay are
> one number, applied to both paths, or the release is a regression.

This is why it is 8.0.0 and not 7.7.0.

## 5. Proposed design

### 5.1 One clock

Introduce a single receiver-side presentation clock:

```
presentAtNs(frame) = senderTimestampNs(frame) - clockOffsetNs + targetDelayNs
```

- `senderTimestampNs` — from the mirror header (§3.1), pending verification.
- `clockOffsetNs` — from the NTP exchange Ferry already runs (§3.2/3.3).
- `targetDelayNs` — the smoothing buffer. One number, applied to audio and video alike.

Frames then present on the *sender's* cadence rather than the *network's*, which is exactly the
substitution that removes jitter. A variable-rate source (iOS sends video only when the screen
changes) is handled naturally, because the schedule comes from the source's own timeline rather than
from an assumed frame rate.

### 5.2 Video: scheduled release, snapped to vsync

Replace `releaseOutputBuffer(index, render)` with `releaseOutputBuffer(index, presentAtNs)`, with
`presentAtNs` snapped to the nearest panel vsync boundary learned from `Choreographer`.

This is the technique `androidx.media3`'s `VideoFrameReleaseHelper` implements, and it is the
reference to study. Media3 is Apache 2.0, which flows into GPLv3 cleanly — the same direction that
forced Ferry to GPLv3 in the first place — so the approach, and if useful the code, can be adopted
with a `NOTICE` entry.

### 5.3 Audio: the same delay, and a setpoint that stops being a magic number

`AudioStreamServer`'s catch-up controller currently drives the jitter queue toward a depth of 4
packets. Four is a constant with no derivation; it is "shallow but not empty."

Under a presentation clock it becomes derived: the target depth is *whatever depth corresponds to
`targetDelayNs`*. The controller does not change shape — it still nudges playback ±2% with wide
hysteresis, which works — but it starts steering toward a number that means something.

This also fixes a defect visible in the current logs: catch-up engages and disengages **dozens of
times a minute** ("draining 12 … back to target … draining 12 …"). 6.8.0's own comment says constant
engagement "would mean the queue is refilling as fast as it drains — a different problem." That is
what is happening: the 12/4 band is too narrow for bursty delivery, so the audio is being pitch-
shifted almost continuously.

### 5.4 Choosing `targetDelay`

Start fixed and conservative. **80 ms** is the proposal: comfortably more than the observed burst
spread, comfortably less than the ~150 ms where lip-sync error becomes noticeable on speech, and
small against the delays already present in the chain (the AudioTrack buffer alone is ~64 ms).

Adaptive sizing — measuring inter-arrival jitter and tracking it — is deliberately **out of scope
for 8.0.0**. It is the right end state and the wrong thing to introduce alongside the mechanism it
depends on.

## 6. Risks, and what is done about each

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| 1 | **The header timestamp is not there, or is not usable.** The whole design rests on §3.1, which is currently an inference from an ancestor's source and a plan document. | Fatal to the design | **Stage A exists solely to settle this before anything else is built.** Fallback: derive cadence from smoothed arrival times instead. Less accurate, still a large improvement over none. |
| 2 | **Back-pressure.** Scheduled release makes the codec hold buffers until their moment — the exact hazard `VideoDecoder`'s current comment warns about, and a cousin of the 6.5.0 BufferQueue jam. | High | Cap in-flight scheduled buffers at the BufferQueue depth (3, the same bound 7.6.0 already uses). If input buffers start starving, fall back to immediate release and say so on the HUD. |
| 3 | **A static screen.** iOS sends nothing for minutes, then one frame. A stale schedule would delay it, or worse, present it in the past. | High | If `presentAtNs` is behind now, or absurdly far ahead, present immediately and re-anchor the clock. |
| 4 | **Clock drift** over a long session. | Medium | Correct the anchor slowly and continuously; never jump. A jump is a visible stutter, which is the thing being fixed. |
| 5 | **A/V sync regression** — the one that could make things worse rather than better. | High | Video and audio delay ship together (§4), never separately. Sync is verified on hardware before the setting defaults on. |
| 6 | **It does not work.** | Medium | The whole thing sits behind a setting, default **off**, so nobody who is not testing it can be hurt. Abandon criteria in §8. |

## 7. Staged plan, with a gate at each stage

Each stage ships and is verified on hardware before the next is written. No stage assumes the next
one will happen.

**Stage A — observe, change nothing.**
Parse the full 128-byte header. Log candidate timestamp fields and whether they advance
monotonically at the frame rate. Surface the NTP offset in diagnostics. **Ships with zero behaviour
change.**
*Gate:* a diagnostics log from real casting showing a usable per-frame timestamp — or showing there
isn't one, which sends us to the §6.1 fallback.

**Stage B — video scheduling, behind a setting, default off.**
Presentation clock, vsync snapping, scheduled release, in-flight cap, fallbacks per §6.
*Gate:* `SHOW /s` tracks `VIDEO fps`, and it looks smooth on the TV.

**Stage C — audio alignment.**
Same delay on the audio path; catch-up setpoint derived from it.
*Gate:* lip sync verified on speech content, and catch-up stops oscillating.

**Stage D — default on**, once A–C hold on hardware over more than one session.

## 8. Abandon criteria

Stated now, so the decision is not made while attached to the work:

- If Stage A finds no usable timestamp **and** arrival-time smoothing does not measurably reduce
  display jitter, stop. The remaining choppiness is the network, and the honest answer is that a
  receiver cannot fix a bursty link.
- If `SHOW /s` does not converge toward `VIDEO fps` at Stage B, the model is wrong. Revert; do not
  tune constants to rescue it.
- If sync error is audible at Stage C and cannot be fixed within one iteration, revert the whole
  thing. Choppy-but-synced beats smooth-but-lipsynced-wrong.

## 9. Not in this release

Recorded so they are not smuggled in:

- Adaptive buffer sizing (§5.4).
- The audio boost's latency being invisible to the sync controller — the boost sits downstream of
  the queue, so any delay it adds cannot be measured or drained. Real, separate.
- Debouncing receiver restarts on rapid settings changes. Real, unrelated, small.
- DACP identity and last-reported volume leaking across sessions. Real, unrelated, small.

## 10. Open questions

1. Which offset in the 128-byte header carries the timestamp, in what units, on what clock? **Stage A
   answers this. Everything else is downstream of it.**
2. Does Fire OS 7 / API 28 honour `releaseOutputBuffer(index, timestampNs)` on `OMX.MTK.VIDEO.
   DECODER.AVC`? It is API 21+ and should, but "should" is what this project keeps being wrong about.
3. Is 80 ms the right starting delay, or should Stage B ship a picker so it can be judged on the
   actual screen rather than argued about here?
