# Release 6.0.0 — plan

Status: **implemented**. Written 2026-08-05 against `v5.5.0` (`d9fdc9f`, versionCode 18);
shipped as 6.0.0 / versionCode 19. This document is the diagnosis — the reasoning for
*why* each of these is a bug, which the CHANGELOG summarises but does not derive. Keep it
for the next time one of these areas is touched.

Scope decision taken: **strip Miracast and Cast from the Fire TV build only**, keeping the
`googletv` flavor and its real Cast Connect implementation intact.

Four things were reported from the Fire TV after 5.5.0. Every one of them is
reproduced below as a specific code path, because three of the four are not the
bug they look like from the couch.

Reported:

1. Lagging, frames glitching, the picture hanging for a very long time,
   sometimes to the point of a crash. New in 5.5.0; survives a Firestick restart.
2. Ferry keeps advertising itself even when the app is not open.
3. Two of the three cast options do nothing on a Fire TV.
4. Closing a cast manually raises an error; the error then sticks, but casting
   still works if you start it again.

---

## A. The freeze cascade (report 1) — a 5.5.0 regression

`v5.5.0` contains one change: `VideoDecoder.INPUT_BUFFER_WAIT_MS` 4 ms → 16 ms.
`v5.0.1` had already added `KEYFRAME_INPUT_BUFFER_WAIT_MS` = 100 ms. Both are
blocking waits inside `decodeNalUnit`, and `decodeNalUnit` runs on
`MirrorStreamServer.runDecoder` — **the same thread that drains the frame queue**.

The cascade:

1. The codec is momentarily busy. The decoder thread blocks up to 16 ms — a
   whole frame budget at 60 fps — or up to 100 ms (≈6 frames) if the frame
   carries an IDR.
2. The reader thread keeps enqueuing. `QUEUE_CAPACITY` is 16 (~267 ms).
3. The queue overflows. If no queued frame is disposable — iOS low-delay
   encoders routinely mark every slice as a reference, and `classify()` is
   deliberately conservative — `enqueue` falls to case 3: drop the oldest,
   set `awaitingKeyframe`, bump `resyncArmSeq`.
4. `decodeFrame` now skips **every** non-keyframe for up to
   `RESYNC_GIVE_UP_MS` = **3 seconds**.

That alone explains "hung for a very long time". But there is a second-order
effect that makes it self-sustaining:

> The 100 ms keyframe wait is itself long enough to overflow the queue *while
> the IDR is in flight*. When that happens `resyncArmSeq` has moved, so the
> `resyncing && resyncArmSeq == armSeqBefore` guard refuses to clear
> `awaitingKeyframe` — **the keyframe wait causes the overflow that invalidates
> the keyframe it was waiting for.**

Result: 3 s frozen, a moment of motion, 3 s frozen. Which reads exactly as a
TV that has locked up.

The 5.5.0 commit justified the longer wait with "with one frame queued, the
extra 12 ms delays nothing behind it". True at queue depth 1 — and nothing
anywhere enforces depth 1. The wait needs to collapse as queue depth rises;
that back-pressure guard does not exist.

Each individual piece here (the 16 ms wait, the 100 ms keyframe wait, the
`resyncArmSeq` guard, the 3 s give-up) was a defensible fix for the bug in
front of it in 5.0.0–5.5.0. Together they form a loop. This is the part of
6.0.0 that wants a rethink rather than another constant.

**Fix direction:** make the input-buffer wait a function of queue occupancy
(near-empty → wait; backing up → drop immediately); re-examine whether the
resync machinery still earns its keep once the wait can no longer cause the
overflow.

## B. One exception kills the decoder for the whole session (report 1, the crash/hang)

`MirrorStreamServer.runDecoder`:

```kotlin
try {
    while (running) { ...decode... }          // catch is OUTSIDE the loop
} catch (e: Exception) { ... }
finally { decoder?.release(); decoder = null }
```

`configureDecoder` → `rebuildDecoder` → `VideoDecoder.initialize` can throw:
`MediaCodec.createDecoderByType`, `codec.configure`, and `CodecException` are
all unchecked. One transient failure exits the loop **permanently**. `running`
is still true, so the reader thread keeps filling a queue nobody drains — every
frame dropped, picture frozen until the sender reconnects.

Related leak: when `initialize` throws part-way, `HandlerThread("FerryVideoDecoder")`
has already started, and because `decoder = VideoDecoder(...).also { initialize }`
never completes the assignment, `release()` is never called. One leaked thread
per failure.

**Fix direction:** the catch belongs inside the loop, around a single item, with
a bounded retry/backoff. `initialize` must clean up its own partial state.

## C. Advertising while the app is closed (report 2)

`MainActivity.onDestroy` stops the service only `if (isFinishing)`. On Fire TV
the Home button produces `onStop` and no destroy, so the service keeps running
and keeps `_airplay._tcp` + `_raop._tcp` registered on port 7000 indefinitely.
`START_STICKY` and `BootReceiver` widen the same hole.

The safety instinct behind the report is right, and it is worse than untidy:
`airPlayPinAuthEnabled` defaults to **false**, so while the app looks closed,
anything that can reach the subnet can put video and audio on the screen. The
network perimeter is the only control in the default configuration
(`AppSettings` documents this honestly; the interaction with an invisible
always-on receiver is what is new).

**Fix direction:** advertise only while the app is open, as the default, with an
explicit opt-in for always-on. Retire the reflexive `START_STICKY` resurrection.
Decide what `startOnBoot` means once advertising is scoped to the foreground.

## D. Two dead protocols (report 3)

**Cast on Fire TV** — `app/src/firetv/.../CastReceiver.kt` is a literal no-op
stub that logs and reports `DISABLED`. Fire TV has no Play Services, so this is
honest, but it still ships a Settings toggle and a Home card that can never do
anything. (`castEnabled` defaults to `true`.)

**Miracast on Fire TV** — worse than dead. `registerP2pService()` gates on
`hasWifiP2pPermission()`, which checks `ACCESS_FINE_LOCATION` /
`NEARBY_WIFI_DEVICES`. **Neither is ever requested at runtime** — `MainActivity`
requests only `POST_NOTIFICATIONS`. So on every Fire TV, every boot, the check
fails and the receiver emits `ProtocolState.ERROR`. It never advertises, never
opens port 7236, and paints a permanent red error card. (`miracastEnabled`
defaults to `true`.)

So one of the two "extra" options is inert and the other is a permanent error
light. Removing them from the Fire TV build also drops `CHANGE_WIFI_STATE`,
the capped location permissions and `NEARBY_WIFI_DEVICES` from the manifest.

> Note for scoping: the **googletv** flavor's `CastReceiver` is a real Cast
> Connect implementation. It reports `ERROR` today only because `CAST_APP_ID`
> defaults to empty. Whether 6.0.0 deletes these protocols outright or only
> removes them from the Fire TV flavor is the open decision.

## E. The sticky error (report 4)

This is the one whose surface behaviour ("error shows, but casting still works")
is the actual diagnostic clue.

`AirPlayReceiver.onStreamingStopped()` calls `mdnsService?.restart()` on **every**
session end. Nothing ever unregistered mDNS during the session, so the whole
teardown/re-register is pure churn — and it is the churn that breaks things:

- `MdnsService.restart()` = `stop()` (an **async** `unregisterService`) followed
  immediately by `start()` registering the same names. That is a race.
- `onRegistrationFailed` emits `ERROR` and sets `isStarted = false`, but does
  **not** clear `airPlayListener` / `raopListener` and never retries. The next
  `start()` overwrites those fields — an NsdManager listener leak per cycle.
- `ADVERTISING` is only emitted when `registeredCount` reaches 2. If one of the
  two registrations fails, the counter never gets there, so **the card stays
  `ERROR` for the rest of the process lifetime** even though the other service
  is live.

Meanwhile `RtspHandler` on port 7000 is entirely independent of mDNS and keeps
listening, and senders cache the record — which is exactly why casting still
works while the UI insists there is an error.

**Fix direction:** stop restarting mDNS on session end (it was never
unregistered). Make registration failure recoverable — clear listeners, back off,
retry — and derive the advertising state from what is actually registered rather
than from a counter that only counts up.

## F. Smaller cleanups swept into 6.0.0

- `AppSettings.mirrorAudioEnabled` KDoc says it "defaults OFF" and warns that
  enabling it "can make macOS tear the whole mirror session down after a couple
  of seconds". The value is `true`, and has been since the initial commit. Either
  the doc or the default is wrong, and if the doc is right this is a second
  session-death cause. **Needs settling against real behaviour, not by editing
  whichever one is easier to change.**
- `ServiceController.stop()` uses `context.startService()`. If the service is not
  already running and the app is backgrounding, that throws on API 26+.
- `MainActivity.onDestroy` calls `super.onDestroy()` before doing its own work.
- `FerryService.startMiracast/startCast` optimistically set `ADVERTISING` before
  the receiver has reported anything.
- `ServiceState.Error` exists and is rendered by `HomeFragment`, but nothing ever
  sets it.
- The notification's Stop action stops the receivers with no path back from the
  app UI.

## What only the TV can settle

Per the toolchain notes, there is no emulator and no adb path to the user's Fire TV, so
none of the following was verified here:

1. **Whether the freezes are gone.** The mechanism is understood and the guard is tested,
   but "understood" is what 5.5.0 also had. With the debug overlay on, `keyframeWaits` is
   the number that matters — each one was a resync that could stop the picture for up to
   3 seconds.
2. **Whether anything remains once they are.** If freezes persist while `keyframeWaits`
   stays near zero, the cause is not this cascade, and the next suspect is `mirrorAudioEnabled`
   (see F) — macOS tearing the session down over RTCP clock-sync would look similar from
   the couch and has nothing to do with the decoder.
3. **That leaving the app really does drop the mDNS registration**, i.e. Ferry disappears
   from the iPhone/Mac picker within a few seconds of pressing Home.
